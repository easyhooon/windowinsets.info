#### 부제: 사이드 버튼, 설정 메뉴, File Browser에서 막힌 측정 흐름을 고친 과정

## 서두

Samsung Remote Test Lab(RTL) 기기를 예약하고 Astra에게 InsetsProbe로 WindowInsets를 측정해 달라고 했다. 앱을 설치하고 화면을 조작하면 될 줄 알았는데, 처음 막힌 곳은 측정 코드가 아니었다.

화면이 검게 보일 때 기기를 깨우는 **사이드 버튼**을 찾는 데 헤맸다. 제스처 내비게이션으로 바꾸려고 **설정 앱의 메뉴**를 찾아가는 과정도 매끄럽지 않았다. JSON을 저장한 뒤에는 RTL **File Browser에서 파일을 내려받는 일**이 반복 작업의 병목이 됐다.

처음에는 Astra가 이런 UI에서 고전할 거라고 예상하지 못했다. 나보다 훨씬 많은 걸 아는 모델인데, 내가 바로 누를 수 있는 버튼을 왜 못 찾는지 답답했다. 왜 막혔는지 따라가 보니 지식의 문제가 아니라 **화면을 보고 행동한 뒤 결과를 확인하는 경로**의 문제였다. 브라우저, 원격 기기 화면, 기기 프레임, Android 설정 앱이 서로 다른 조작 표면이었다. 그 위에 RTL 다운로드의 불안정성까지 겹쳤다.

이 글은 각 단계에서 실제로 발생한 문제, 확인한 원인, 적용한 해결책을 순서대로 정리한 트러블슈팅 기록이다.

## 본론

### 문제 1. 검은 화면을 깨울 사이드 버튼을 찾기 어려웠다

#### 문제 발생

RTL WebClient에서 Probe APK를 설치해 실행했지만 기기 화면이 검게 보일 때가 있었다. 이때 필요한 조작은 앱 화면의 버튼 클릭이 아니라, WebClient가 그려 주는 휴대폰 **외곽 프레임의 물리 버튼** 클릭이었다.

브라우저의 메뉴는 접근성 트리에서 요소를 찾을 수 있지만, 원격 Android 화면은 대체로 픽셀 스트림이다. 기기 안의 버튼이나 설정 항목에 안정적인 DOM 이름이 붙어 있지 않다. 같은 "버튼"이어도 웹 UI와 기기 프레임, 화면 내부를 각각 다른 방식으로 다뤄야 했다.

<!-- RTL 실제 화면 삽입 1: 검은 원격 화면과 휴대폰 오른쪽 테두리의 아래쪽 사이드 버튼이 함께 보이는 캡처. 캡션: "전원 버튼은 앱 화면이 아니라 RTL이 그린 기기 프레임에 있었다." -->

사람은 휴대폰 그림을 보는 순간 측면의 돌출부가 전원 버튼이라는 맥락을 읽고 누른다. Astra는 **현재 스크린샷에서 그 위치를 추정하고 좌표로 클릭한 뒤, 화면이 켜졌는지 새 스크린샷으로 확인**해야 했다. 검은 화면만 보고 있으면 앱이 꺼진 건지, 기기가 잠든 건지, 클릭이 빗나간 건지도 바로 구분되지 않는다. 추론 능력이 높아도 이 관찰·조작·확인 고리의 정보가 부족하면 간단한 동작에서 시간을 쓴다.

#### 문제 해결

화면이 검다면 먼저 새 스크린샷에서 휴대폰 오른쪽 테두리의 **아래쪽 사이드 버튼**을 찾고 클릭하는 절차를 작업 순서에 넣었다. 이후 화면이 켜졌는지 다시 확인한다. 좌표를 한 번 외워 반복하는 방식은 창 크기나 스트림 배율이 바뀌면 어긋날 수 있어 매번 현재 화면을 기준으로 잡는다.

잠금 화면의 스와이프나 인증이 원격 스트림에서 안정적으로 처리되지 않을 때는 그 단계를 사람에게 넘긴다. 앱이 뜨지 않는 상태에서 Probe 측정 로직을 계속 고치는 것보다, **기기가 깨어 있고 잠금이 풀렸는지** 먼저 분리해 확인하는 편이 빨랐다.

### 문제 2. 설정 메뉴를 한 번 스크롤하자 이전 스크린샷이 쓸모없어졌다

#### 문제 발생

WindowInsets는 제스처와 3버튼 내비게이션에서 값이 달라진다. 두 모드를 측정하려면 Android **설정 → 디스플레이 → 내비게이션 바**로 들어가야 한다. Astra는 스크린샷을 보고 메뉴를 찾았지만, 설정 화면을 한 번 스크롤하면 항목의 위치와 보이는 범위가 달라졌다. 직전 스크린샷에서 찾은 위치를 다음 클릭에 그대로 쓰면 엉뚱한 항목을 누르거나 빈 곳을 누르게 됐다.

나는 스크롤 중에도 같은 목록을 계속 보고 있어서 항목이 어디로 이동했는지 따라갈 수 있었다. Astra의 조작은 **스크린샷 A에서 판단 → 스크롤 → 달라진 화면 B에서 다시 판단**하는 식으로 끊겼다. 이때 B를 새로 읽지 않고 A의 좌표나 메뉴 맥락을 이어 쓰면, 그 다음 화면도 예상과 달라져 다시 헤매는 일이 반복됐다.

<!-- RTL 실제 화면 삽입 2: 설정 메뉴를 스크롤하기 전과 후의 화면을 나란히 배치. 캡션: "한 번 스크롤하자 찾던 항목의 위치와 화면에 보이는 메뉴가 달라졌다." -->

때로는 Probe에서 설정을 열려고 해도 설정 화면으로 넘어가지 않고 Probe가 계속 전면에 남았다. 메뉴를 찾는 것과 앱 사이를 왕복하는 것 모두 측정 시간의 일부가 됐다. 사람에게는 "내비게이션 바를 열어"라는 한 문장이지만, 원격 조작에서는 현재 화면 식별, 스크롤, 항목 선택, 모드 변경, 앱 복귀, 변경 확인이 각각 별도 단계다.

처음에는 앱에서 `Settings.Secure.putInt(navigation_mode, ...)`로 모드를 바꾸는 자동화도 시도했다. 코드의 자동 실행 경로에 모드 변경 호출이 빠진 오류를 고친 뒤에도 실제 Samsung 기기에서는 요청이 적용되지 않았다. 새 캡처는 여전히 3버튼 모드였다.

#### 문제 해결

Probe에 **Display / navigation settings** 버튼을 두어 Android 디스플레이 설정을 바로 열게 했다. 그 뒤에는 스크롤할 때마다 **새 스크린샷을 찍어 현재 보이는 메뉴와 위치를 다시 확인**하고, 그 화면에서 찾은 항목만 누르도록 절차를 바꿨다. **내비게이션 바**를 찾으면 **스와이프 제스처**를 선택한 뒤, 왼쪽 가장자리 뒤로 가기로 Probe에 돌아온다.

설정 앱으로 이동이 막히는 경우를 위해 상단에 **× 종료 버튼**도 추가했다. Probe 작업을 닫은 뒤 설정으로 이동할 수 있게 한 것이다.

내비게이션 모드는 실제 설정 화면에서 사람이 전환한다. Probe로 돌아와 새로 측정하고, JSON의 `navigation.mode`와 설정 상태를 함께 확인한다. 앱이 설정값을 썼다는 로그나 파일명만으로 모드 변경을 인정하지 않는다.

### 문제 3. JSON은 저장됐는데 File Browser 다운로드가 오래 걸렸다

#### 문제 발생

기존 흐름에서 파일을 받으려면 RTL File Browser의 `Android/data/info.windowinsets.probe/files`로 이동해야 했다. JSON 행에 마우스를 올려야 다운로드 아이콘이 나타났다. 내려받은 파일 이름도 원래의 `main-gesture.json`이 아니라 `content`, `content (1)`처럼 바뀌었다.

<!-- RTL 실제 화면 삽입 3: File Browser에서 JSON 행에 마우스를 올려 다운로드 아이콘이 드러난 화면. 가능하면 브라우저에 저장된 content 파일명도 함께 캡처. 캡션: "저장된 JSON은 보이지만 다운로드 버튼은 행에 마우스를 올려야 나타났다." -->

따라서 파일 하나를 받을 때마다 실제 JSON을 열어 모델, 화면, 내비게이션 모드, 창 크기, 시각을 확인하고 올바른 증거 경로에 배치해야 했다. 예약 시간이 정해진 RTL에서 이 작업은 단순한 클릭 몇 번이 아니었다.

Galaxy Z Flip3에서는 3버튼 캡처는 호스트에 도착했지만, 기기에 저장된 제스처 캡처의 후속 다운로드가 전달되지 않았다. Chrome 자동 다운로드가 허용된 상태였고 클립보드 전송도 시도했지만 호스트에는 오지 않았다. 결국 다음 예약에서 다시 측정해 받아야 했다. 파일이 기기에 존재한다는 사실과 내 컴퓨터로 전달됐다는 사실도 따로 검증해야 했다.

#### 문제 해결

우선 File Browser에서 **경로 이동 → 행에 마우스 올리기 → 다운로드 → JSON 내용 검증**을 정해진 순서로 만들었다. 브라우저 파일 이름 대신 JSON 내부 필드로 캡처를 식별하고, 못 받은 파일은 받은 척하지 않았다.

반복되는 다운로드 경로를 줄이기 위해 Probe가 JSON을 `/api/captures`로 직접 보내는 기능도 추가했다. 서버는 원본 파일을 `capture-inbox` 브랜치에 업로드당 한 커밋으로 남긴다. 캡처마다 PR을 열거나 데이터를 검증하지 않고, 하나의 PR에 여러 업로드를 모은 뒤 병합 시점만 내가 결정한다. 병합할 때는 스쿼시해 `main`에는 한 커밋으로 남긴다.

다만 2026년 9월 27일 기준 실제 GitHub 업로드는 아직 검증 전이다. 첫 Vercel 프리뷰에서는 API가 404였고, 함수를 배포한 뒤에는 ESM import 오류로 500이 났다. 설정과 import를 고친 프리뷰는 GET 405, 토큰 없는 POST 503까지 확인했다. PAT 등록 후 실제 업로드를 시험해야 한다.

### 문제 4. 파일이 생겨도 잘못된 화면을 측정할 수 있었다

#### 문제 발생

Galaxy Z Fold8의 과거 `main` JSON은 `1248 × 1972 px`이었다. 이 크기는 내측 화면이 아니라 공식 커버 화면과 일치한다. 당시 어떤 버튼 순서로 그 파일을 만들었는지는 로그만으로 확정할 수 없다.

하지만 옛 **Measure All**에는 분명한 결함이 있었다. Cover/Main 버튼은 파일의 라벨만 바꿨고 폴더블의 실제 화면은 전환하지 않았다. 내비게이션 변경도 기기에서 적용되지 않았다. 파일에 붙인 화면·내비게이션 라벨과 Android가 실제로 보고한 상태가 달랐다.

#### 문제 해결

Measure All을 제거하고, 폴더블의 접힘 상태는 RTL의 실제 기기 제어로 바꾼다. 캡처 전 현재 창 크기를 공식 화면 크기와 대조한다. Fold8은 커버 `1248 × 1972 px`, 내측 `2448 × 1848 px`를 따로 다시 측정했다. 과거 JSON은 고치지 않고 이력으로 남겼다.

Probe가 확실히 제어할 수 있는 범위는 **활성 화면의 회전**이었다. 지금의 회전 스윕은 세로·가로·역방향 가로를 요청한 뒤 창의 실제 형태와 인셋 콜백을 확인한다. 마지막 변경 뒤 700ms 동안 안정되면 새 값을 저장하고, 6초 안에 회전하지 않으면 그 방향은 건너뛴다.

Android는 큰 화면이나 제조사 설정에 따라 [`setRequestedOrientation()` 요청을 무시할 수 있다](https://developer.android.com/reference/android/app/Activity#setRequestedOrientation(int)). 그래서 가로 화면이 나오지 않았는데 세로 값을 돌려 가로 측정값으로 저장하지 않는다.

### 문제 5. 내가 직접 받는 편이 빨랐지만 120종을 반복할 수는 없었다

#### 문제 발생

결국 9월 26일부터는 "이럴 거면 내가 더 번거롭고 말지" 하고, 내가 기기를 조작해 다운로드 파일을 Astra에게 건네는 방식으로 진행했다. 한 대씩 보면 내가 버튼을 찾고 파일을 받는 편이 빨랐다. Astra가 헤매는 동안 내가 데이터를 꾸역꾸역 넣어 준, 말 그대로 **인간 데이터 수집기**가 된 셈이다.

그런데 가로 모드를 추가하려고 보니 약 120종을 다시 예약하고, 각 기기에서 화면 방향을 바꿔 찍고, 파일을 받아 전달해야 했다. 기종이 늘고 커버·내측 화면이나 내비게이션 모드까지 나뉘면 같은 수작업이 계속 불어난다. 한 번의 작업에서 빠른 방법이 전체 측정 규모에서는 병목이 됐다.

#### 문제 해결

사람이 해야 하는 **기기 예약·잠금 해제·접힘 상태와 내비게이션 모드 준비**를 측정 자체와 분리했다. 준비가 끝난 화면에서는 Probe가 실제 회전을 확인하며 방향별 JSON을 만들게 했다. 파일 전달은 직접 업로드 API로 줄이려 하지만, 아직 실전 업로드 검증이 남아 있다.

따라서 지금의 해결은 완전 무인화가 아니다. 매번 사람 손으로 눌러야 할 동작을 줄이고, 측정값의 화면·방향·모드가 맞는지 확인할 지점을 명확히 한 것이다. 다음 기종을 추가할 때도 같은 절차를 다시 쓸 수 있도록 작업 순서와 실패 사례를 남겼다.

## 결론

처음에는 Astra가 사이드 버튼이나 설정 메뉴를 찾는 데 그렇게 오래 걸릴 줄 몰랐다. RTL 화면을 자동화하면서 알게 된 것은 **웹의 접근 가능한 요소**, **원격 기기의 픽셀 화면**, **기기 프레임의 버튼**이 같은 조작 대상이 아니라는 점이었다.

해결책도 프롬프트 한 줄을 더 자세히 쓰는 데서 끝나지 않았다. 화면을 깨우는 순서를 문서화하고, 설정으로 나가기 쉽게 Probe를 고쳤다. File Browser의 숨은 동작과 불안정한 다운로드는 검증 절차로 다루면서 직접 업로드 경로를 만들었다. 잘못된 화면 라벨 문제는 실제 창 크기와 기기 상태를 확인하는 방식으로 바로잡았다.

현재는 **사람이 기기 화면과 내비게이션 모드를 준비하고, Probe가 가능한 회전을 측정하는 반자동 흐름**이다. 업로드까지 실제로 통과하면 파일을 옮기는 시간이 줄어든다. 업로드된 원본 JSON을 사람이 매번 검증하는 절차는 두지 않았다. 120종을 다시 찍어야 한다는 부담이 자동화를 고친 직접적인 이유였다.

인간 데이터 수집기를 졸업하려면 Astra도 더 똑똑하게 움직여야 한다. 스크롤 뒤에는 이전 좌표를 버리고 새 화면을 확인하고, 다운로드를 눌렀다면 파일이 실제로 도착했는지 확인해야 한다. 반복 측정과 전송은 Probe와 업로드 경로에 맡긴다. 자동화가 만들어 낸 파일보다 실제 기기가 보여 준 상태를 믿는 절차까지 갖춰야 다음 기종을 감당할 수 있다.
